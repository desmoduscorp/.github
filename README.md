# Desmodus

**Engineering for difficult software and systems problems.**

Desmodus is an engineering consultancy focused on software architecture, infrastructure, automation, AI systems, and operational tooling.

We approach technology as a means to solve problems, not as the starting point.

## What we work on

Our work tends to sit where software, infrastructure, and operations meet:

* Software architecture
* Distributed systems
* Infrastructure and developer tooling
* Automation
* AI systems
* Operational bottlenecks
* Internal platforms and technical tooling

The specific technology matters less than understanding the system around it.

## Open source

We publish tools when we believe they are useful beyond the problem that originally motivated them.

Our open-source work follows a few simple principles:

* **Small, focused tools over large abstractions**
* **Clear behaviour over hidden complexity**
* **Useful defaults without removing control**
* **Minimal dependencies where practical**
* **Documentation as part of the interface**
* **Correctness before convenience**

Not everything we build belongs in open source. When it does, the objective is to release something that can stand on its own and remain useful without depending on Desmodus.

## Engineering principles

### Problems before tools

We start by understanding the constraints, failure modes, and surrounding system before choosing technologies.

### Systems over components

A technically correct component can still make the wider system worse. Interfaces, incentives, operations, and failure behaviour matter.

### Explicit trade-offs

There is rarely a universally correct architecture. Decisions should make their assumptions and costs visible.

### Simple where possible

Complexity is sometimes necessary. Accidental complexity is not.

### Understand before automating

Automation amplifies whatever process already exists. A poorly understood process usually becomes a poorly understood automated process.

## Contributing

Our public repositories are open to issues, discussions, and pull requests.

Each project may define its own contribution guidelines, but in general we value:

* Clear problem descriptions
* Small and reviewable changes
* Tests for behavioural changes
* Technical reasoning behind non-obvious decisions
* Constructive disagreement

If you are unsure whether a change belongs in a project, opening an issue before implementing it is usually the best place to start.

## Security

Please do not disclose security vulnerabilities through public issues.

Security reporting instructions will be provided in the relevant repositories.
